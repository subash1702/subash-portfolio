Change Data Capture (CDC) Pipeline

A change-driven data synchronization pipeline that captures updates from two PostgreSQL source systems, transports database changes through Kafka, and incrementally applies them to Delta Lake target tables.

PostgreSQL Debezium Kafka Connect Apache Kafka Databricks Spark PySpark SQL Delta Lake

What it does

  • Captures database changes from two PostgreSQL source systems through change data capture instead of relying on recurring full-table refreshes.
  • Uses Debezium and Kafka Connect to capture and integrate change events, with Kafka as the event transport layer.
  • Processes changes incrementally using Databricks, Apache Spark, PySpark, and SQL.
  • Applies merge-based updates to Delta Lake target tables across 15+ production tables.
  • Reconciles source and target data to check synchronization and identify discrepancies.

Architecture

The pipeline captures source changes, transports them as events, processes only the affected data, and applies updates to the target. Reconciliation checks support source-to-target consistency.

PostgreSQL → Debezium/Kafka Connect → Kafka → Databricks Spark/PySpark and SQL → Delta Lake, with reconciliation.

Workflow

The workflow is organized into five stages. Each stage has a clear responsibility, from detecting a database change to verifying that the downstream target reflects it.

Change events flow through each stage; reconciliation is performed against source and target data after synchronization.

How it works

1. Capture changes at the source. Two PostgreSQL systems act as the upstream data sources. Instead of repeatedly extracting entire tables, the CDC path captures database changes for downstream processing.

2. Connect and publish events. Debezium runs with Kafka Connect to capture and integrate change events. Kafka provides the event transport layer between capture and processing, keeping the upstream capture path separate from downstream jobs.

3. Process only the changed data. Databricks uses Apache Spark with PySpark and SQL for incremental processing. This change-driven approach reduces the work required compared with repeatedly refreshing the full dataset.

4. Apply changes to target tables. Merge-based synchronization writes incoming changes into Delta Lake targets, updating existing records or applying new records as appropriate. The pipeline covers 15+ production tables.

5. Reconcile and validate. Source-to-target reconciliation is used to check the resulting data and surface discrepancies. This provides a validation step beyond simply confirming that events were delivered.

Why CDC instead of recurring full loads?

With periodic full or broad batch refreshes, downstream data can remain stale until the next scheduled run, and the pipeline may reprocess unchanged records. CDC shifts the synchronization pattern toward change-driven updates: capture what changed, transport those changes, and apply them to the target. This is especially useful when data freshness matters and the upstream systems continue to receive updates throughout the day.

Data consistency and operational considerations

  • Incremental scope: Processing is focused on captured changes rather than reloading all source records each cycle.
  • Merge behavior: Target-side merge operations support applying updates to existing data as well as incorporating changed records.
  • Validation: Source-to-target reconciliation checks the synchronized state and helps identify discrepancies.
  • Decoupled stages: Kafka separates capture from the downstream Spark processing layer, so the pipeline is not a single tightly coupled operation.
  • Freshness: CDC supports a shorter synchronization window than the prior batch-oriented process.

Engineering considerations

  • CDC reduces reliance on repeated full-table extraction when only a subset of records has changed.
  • Kafka provides a boundary between database change capture and the processing layer.
  • Incremental processing and Delta Lake merge operations support targeted synchronization.
  • Reconciliation is important because event transport alone does not prove source-to-target consistency.
  • The approach is useful when freshness requirements justify change-driven processing.

Conclusion

This pipeline moved synchronization from a slower batch-oriented pattern toward change-driven processing. Debezium and Kafka Connect captured updates from two PostgreSQL systems, Kafka transported the events, and Databricks Spark/PySpark with SQL applied incremental merge updates to Delta Lake across 15+ production tables. Source-to-target reconciliation supported consistency checks. The result was synchronization latency reduced from approximately eight hours to under five minutes, along with a 25% reduction in processing time.
